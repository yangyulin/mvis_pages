Use this page to understand the `.mvisdb` file behind every MVIS run:
what it holds, where it lives and how to read it.

A `.mvisdb` file is one SQLite database per recording. It has two parts:

- **Capture core:** the expensive data, board detections and the full IMU streams.
  It is written once and then sealed with a hash of its contents.
- **Run overlay:** one per run (`run_id`), written by each solve.
  It records what the run used, why it left the rest out, and every estimate.

What this gives you:

- **Detection runs once.** A second solve of the same frames with the same board reuses the sealed core, whatever its solve settings.
- **Deleting a run** deletes its whole overlay and leaves the core alone.
- **Every result can say why.** Each frame, board pose and corner the solve left out carries an
  `exclude_reason` and the stage that excluded it.

## Where it lives

| Run | File |
|---|---|
| `mvis cam` | `detections.mvisdb` in the run folder (`-o`). Clearing the run folder keeps it |
| `mvis cam-imu` | One file per recording in `input.cache_dir`. Without `cache_dir` there is no cache |

The cache is keyed on the recording (source, topics or folders, time window) and the board
definition, including the detector settings. Two runs that read different topics or windows of
one bag never share an entry.

:::caution[New detector code needs a fresh cache]
The key does not include the MVIS version. If you update MVIS and want to compare detection,
delete the cache first; otherwise the new version reuses the old detections.
:::

## Read it from Python

```python
from mvis.mvisdb.manager import DatabaseManager

db = DatabaseManager()
path = "results/run/detections.mvisdb"
print(db.capture_info(path))           # name and hashes of the recording
print(db.runs(path))                   # the runs stored, oldest first
capture = db.load(path, run_id=db.latest_solved_run_id(path))
print(len(capture.streams), "cameras,", len(capture.imus), "IMUs")
```

`load` returns one `MVISDatabase` with that run's overlay folded into the objects,
so pipeline code never sees SQL.
Any SQLite client can also open the file directly.

This is the in-memory structure. There is one `MVISDatabase` per recording,
with one run's overlay folded in as flags.

- **Notes** are on the right.

## On-disk form

The same structure is stored in four groups of tables:

| Group | Tables | Notes |
|---|---|---|
| **Meta** | `schema_meta` | Schema version and when the file was created |
| **Capture core** | `capture`, `camera`, `imu` / `imu_meas`, `board` / `board_pt`, `rig`, `stereo_pair`, and the observations `frame` → `board_detection` → `detection` | Corner and IMU arrays are packed float64 blobs. Sealed once `capture.content_hash` is set |
| **Run overlay** (per `run_id`) | `run`; the selection: `frame_status`, `board_detection_status`, `detection_status`; the results: `result_camera`, `result_imu`, `extrinsic` | The selection tables store only rows that differ from "selected and valid". `extrinsic` holds every camera–camera, camera–IMU and IMU–IMU transform with its `T`, time offset and sigmas |
| **Trajectory** (camera–IMU runs) | `estimate_meta`, `state_knot` / `state_var`, `frame_bracket`, `world_frame` | `state_knot` / `state_var`: the state timeline and its variables. `frame_bracket`: which two states bracket each frame, and where. `world_frame`: the gravity-aligned world |

Every overlay table uses `ON DELETE CASCADE`: deleting a `run` row deletes all of its overlay rows.

The status tables mirror the core tables one for one.
That keeps two things cheap: recording each selection decision as it is made,
and checking the stored flags against the data the solve used.
