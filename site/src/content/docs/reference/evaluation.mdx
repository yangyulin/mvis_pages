How to tell whether a calibration is good. The same metrics are used on the
[leaderboard](/benchmark/leaderboard/), so a local run and a published entry are
directly comparable.

## Metrics

| Metric | Units | Computed against | Notes |
|---|---|---|---|
| Reprojection RMSE | px | the run's own observations | Self-consistency only — a run can have low reprojection error and wrong extrinsics |
| Extrinsic rotation error | deg | a reference calibration | Geodesic angle between the two rotations |
| Extrinsic translation error | cm | a reference calibration | Euclidean distance between the two translations |
| Time-offset error | ms | a reference calibration | Per camera and per auxiliary IMU |
| Runtime | s | — | Wall-clock, single machine, hardware reported |
| Convergence rate | % | repeated runs | Successful runs / total runs |

:::caution[Reprojection error is not accuracy]
It measures how well the solution explains the data it was fitted to. A
calibration can fit its own observations tightly and still be wrong — most often
when a parameter was unobservable under the recorded motion and settled
wherever the prior put it. Always read it alongside the reported covariance.
:::

## Simulation: error against ground truth

In simulation the true calibration is known, so error is exact rather than
relative:

```bash
rosrun mvis error_simulation \
  OUTPUT_FOLDER/state_est.txt \
  OUTPUT_FOLDER/state_std.txt \
  OUTPUT_FOLDER/state_gt.txt
```

Read error and σ together — the four cases are set out in
[Simulation & synthetic data](/guides/simulation/#closed-loop-recovery).

## Consistency: NEES

Normalised estimation error squared, averaged over Monte-Carlo runs, tests
whether the reported covariance is honest. It should sit near the state
dimension: consistently above means the estimator is overconfident, well below
means it is conservative. This is what catches a wrong Jacobian — a single run
with small error passes regardless.

## Real data: comparison against a reference

Without ground truth, the check is agreement with an independent calibration —
ideally from a different toolchain, so the two do not share assumptions. This is
what the [examples](/examples/) do: TUM VI against its published `T_cam_imu`,
Monado MSD against the Monado reference.

Two runs of *the same* toolbox agreeing is a repeatability check, not an
accuracy one. Both can be wrong the same way.

## Repeatability across bags

The most practical field check needs no reference at all: calibrate several bags
of the same rig and compare. Parameters that move between bags were not
constrained by the motion in them. This is usually how a weak rolling-shutter
readout or an unobserved g-sensitivity first shows up.
