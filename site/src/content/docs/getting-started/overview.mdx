Use this page to see what MVIS is, what it solves, and how a run works.

MVIS is a Python toolbox that calibrates single- and multi-camera systems.
It is the calibration library behind Open MVIS. It replaces the earlier C++/ROS
implementation.

- **Built on:** GTSAM factor-graph optimisation (one big least-squares problem
  over linked unknowns)
- **Rotations and poses:** native SO(3)/SE(3) Lie group support (3D
  rotations and full rigid poses are handled as their own types)

## What it solves

Everything is solved in **one graph**:

- **Intrinsics** (focal length, centre and other values inside each camera)
- **Distortion**
- **Extrinsics** (where each camera sits relative to the others)
- **Time offsets**
- **Rolling-shutter readout** (the time a camera takes to read its rows top to
  bottom)
- **Board poses**
- **With an IMU:** the camera–IMU transform, IMU intrinsics, and biases

## What makes it different

- **No ROS required.** Pure Python, `pip install`, Linux and macOS.
  - Bags are read through `rosbags`.
  - So a ROS1 or ROS2 recording calibrates on a machine that has never had ROS
    installed.
- **Eight distortion models, mixable.**
  - `radtan`, `kb4` (the fisheye default, also selected by `fisheye` and
    `kannala_brandt`; [why kb4](/why/kb4/)), `equidistant`, `fov`,
    `double_sphere`, `eucm`, `ucm`, and experimental `omni_radtan`.
  - All work in both camera-only and camera–IMU calibration.
  - You can mix them across cameras in one rig.
- **Multi-IMU.**
  - Several IMUs in one graph.
  - Each has its own extrinsics, time offset, and intrinsics.
  - Per-IMU gyro-only mode, for sensors whose accelerometer you cannot trust.
- **It checks its own work.** `mvis roundtrip` applies a calibration to the
  data it came from, then recalibrates.
  - A PASS requires the IMU intrinsics to collapse to identity *and* the
    geometry to stay put.
  - That is a much stronger statement than a low residual.

## Three ways it is used

| Mode | What you do |
|---|---|
| **Full calibration** | Solve everything from a board sequence. |
| **Refinement** | Start from an existing calibration and refine it. Kalibr output reads directly via `mvis.io.kalibr`. |
| **Partial calibration** | Pin what you trust and solve the rest. |

The common partial case is camera–IMU calibration with intrinsics pinned from a
prior camera-only run. This is the recommended two-step workflow.

## Why one graph

Solving jointly keeps the links between errors that pairwise calibration loses.
Calibrating a rig pairwise accumulates error. Each pairwise result carries its
own uncertainty, and composing them discards the correlations between them.

Keeping those correlations matters most for the weakly observable parameters
(the ones the data pins down least):

- time offsets
- rolling-shutter readout
- IMU intrinsics

See [Calibration graph](/concepts/calibration-graph/).

The implementation follows the same principle. Pose interpolation, extrinsic
composition, time offset, rolling shutter, and projection are **one unified
factor**, not a chain of corrections.

## The shape of a run

```
Detection → Quality gating → Init → Per-camera opt → Alignment → Joint opt → Outlier rerun
```

1. **Target and data** — print a board, record with well-excited motion.
2. **Config** — one YAML: board, cameras, optimiser.
3. **Run** — `mvis calibrate -c config.yaml`.
4. **Read** — `*_calib.yaml` to deploy, `*_full.yaml` to replay, and a
   self-contained HTML report.
5. **Validate** — repeatability across sequences, and `mvis roundtrip` for
   camera–IMU.
