Use this page to see how the OpenMVIS trajectory model differs from the one in
Kalibr and Basalt. It also explains why we chose ours.

Both models recover the same calibration; they differ in how they get there:

- **OpenMVIS** solves on a **discrete-time** graph. The trajectory is a set of
  states (snapshots of the rig motion) at measurement times. Pre-integrated inertial
  factors link them: each one sums the IMU samples between two states into a
  single constraint.
- **Kalibr and Basalt** instead represent the trajectory as a
  **continuous-time** B-spline. This is a smooth curve shaped by a set of
  control points. They evaluate every measurement against it.

## The difference

| | Discrete-time (OpenMVIS) | Continuous-time (Kalibr, Basalt) |
|---|---|---|
| Trajectory | states at discrete times | control points of a spline |
| Between states | pre-integrated IMU factor | analytic evaluation of the spline |
| Asynchronous sensors | handled by interpolation and time offsets | handled natively — query at any $t$ |
| Cost per iteration | grows with measurement count | grows with control-point count |
| Model error | none from parameterisation | spline order limits representable motion |

The practical trade is this. A spline evaluates cleanly at *any* timestamp. That
is convenient for rigs whose sensors never sample together.

But a spline imposes a smoothness the true motion may not have. The knot spacing
is the time between knots, the points where the spline's pieces join. If it is too coarse for the actual dynamics,
it biases the calibration. The bias is invisible in the residuals (the leftover
errors after the fit), because the model, not the data, is what is wrong.

## Why the discrete graph is the default here

OpenMVIS is built for multi-IMU rigs. They push against the continuous-time
assumption from two sides:

- **Many clocks.** Each IMU has its own clock and rate. So a single spline must
  be sampled at many inconsistent times.
- **High-rate data.** The high-rate inertial data that makes multi-IMU rigs
  worth having is exactly the content a spline smooths away.

Pre-integration keeps every sample.

## Where continuous time still helps

- **Very high-rate sensors** where per-measurement states would explode the
  graph size.
- **Cross-checking**: since Kalibr is continuous-time, agreement between the two
  is evidence that neither parameterisation is driving the answer. This is part
  of what the [benchmark](/benchmark/methodology/) measures.
- **Rolling shutter**, where a within-frame trajectory query is natural rather
  than an interpolation.

:::note[Not yet implemented]
Continuous-time refinement is a planned addition, not a shipped feature. We
document it here because the benchmark compares against continuous-time methods,
and the distinction explains why results differ. Track it on the
[roadmap](/about/roadmap/).
:::
