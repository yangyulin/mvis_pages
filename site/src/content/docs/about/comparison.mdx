Use this page to see where MVIS sits next to Kalibr and Basalt, the toolboxes
most people already use. Kalibr is mature and widely validated. MVIS is not
trying to displace it on the single-IMU case it does well.

An IMU (inertial measurement unit) is the sensor with a gyroscope and an
accelerometer.

## Feature matrix

| Capability | MVIS | Kalibr | Basalt |
|---|---|---|---|
| Camera intrinsics + distortion | ✅ | ✅ | ✅ |
| Distortion models | radtan, equidistant, FOV, DS, EUCM, omni_radtan | radtan, equidistant, FOV, DS, EUCM | radtan, KB, DS, EUCM |
| **Mixed models across one rig** | ✅ | ✖ | ✖ |
| Camera–IMU extrinsics + time offset | ✅ | ✅ | ✅ |
| **Multiple IMUs** | ✅ | ✖ | ✖ |
| **Per-IMU gyro-only mode** | ✅ | ✖ | ✖ |
| IMU intrinsics (scale, misalignment) | ✅ — 3 conventions | ✅ | ✖ |
| G-sensitivity `Tg` | ✅ | ✅ | ✖ |
| **[Gyro↔accel offset `t_ga`](/benchmark/tga/)** | ✅ | ✖ | ✖ |
| Rolling-shutter readout | ✅ | via fork | ✖ |
| **Corrected-dataset export** | ✅ `apply-calib` | ✖ | ✖ |
| **Round-trip PASS/FAIL validation** | ✅ `roundtrip` | ✖ | ✖ |
| **Batch sweep over a dataset family** | ✅ `input.bags` | ✖ | ✖ |
| Trajectory model | discrete factor graph | continuous-time B-spline | continuous-time B-spline |
| Boards | AprilGrid, chessboard, ArUco | AprilGrid, chessboard, circles | AprilGrid |
| Input | ROS1/ROS2 bag, EuRoC, images, video | ROS bag | ROS bag, EuRoC |
| **Runs without ROS** | ✅ pure Python | ✖ | ✖ |
| Kalibr camchain interop | ✅ read + write | native | ✖ |

## What is actually different

- **No ROS.** MVIS is pure Python via `pip`, on Windows, macOS, and Linux.
  Bags are read with `rosbags`. If you calibrate outside a ROS environment,
  this is the whole story.
- **More than one IMU.** MVIS puts every IMU in one graph. Kalibr and Basalt
  model a single IMU. There, a four-IMU rig has to be calibrated pairwise and
  composed. That accumulates error and throws away the correlations.
- **It fits the gyro–accel offset.** `t_ga` is the time offset between the
  gyroscope and accelerometer channels. Kalibr and Basalt have one IMU clock.
  On the same bags their `td` differs from MVIS by about 2.9–3.2 ms on Looper
  Insight 9 and 1.9–2.0 ms on the T265 (first camera); an injection sweep predicts 3.0–3.2 and
  1.6–1.7 ms of that from the offset alone. Whose `td` is closer to the truth is
  not yet tested. [Details](/benchmark/tga/).
- **Validation is a command, not a habit.** `mvis roundtrip` gives a
  PASS/FAIL. A PASS requires IMU intrinsics to collapse *and* geometry to
  hold. Nothing comparable ships with the others.
- **Discrete-time.** MVIS places state nodes at `state_hz`. Kalibr and Basalt
  fit a B-spline (a smooth continuous-time curve). The trade-off is in
  [Continuous-time refinement](/concepts/continuous-time/).

## Where the others are still ahead

- **Maturity.** Kalibr has a decade of use across the field. MVIS's 228-run
  benchmark is strong evidence, but not the same thing as that.
- **Ecosystem.** Kalibr's target generators, tutorials, and community answers
  have no MVIS equivalent yet.
- **Continuous-time.** Are your sensors genuinely asynchronous at high rate?
  Then a B-spline handles it natively. MVIS does not yet offer it.

## Agreement with Kalibr

This is not a rival claim; it is a validation. On TUM-VI raw IMU bags,
`omni_radtan` and `equidistant` reproduce the Kalibr camera–IMU extrinsics to:

- **≤2 mm lever**
- **≤0.15 mm stereo baseline**
- **≤1 ms time offset**

Camera parameters match the published TUM-VI and Intel T265 calibrations to
under 0.6% on focals.

MVIS also reads Kalibr output directly (`mvis.io.kalibr`). So Kalibr is a
natural source of initial values. Refinement from a Kalibr camchain is a
supported workflow, not a migration.

## Which to use

- **One IMU, one or two cameras, ROS available** → Kalibr.
- **Multiple IMUs, or a gyro-only auxiliary** → MVIS.
- **No ROS on the machine** → MVIS.
- **Rolling shutter** → MVIS, or Kalibr's fork.
- **Mixed camera models on one rig** → MVIS.
- **You need to prove the calibration is right** → MVIS's round-trip.
