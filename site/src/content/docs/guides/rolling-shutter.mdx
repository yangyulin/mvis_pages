Use this page to calibrate a rolling-shutter camera. Such a camera exposes its
rows one after another, so one image spans a range of times.

MVIS solves the **readout time** as a parameter. This is the time the camera
takes to read out its rows. We solve it rather than correcting for it afterwards.

## Enable it

```yaml title="config.yaml"
cameras:
  - camera_id: 0
    shutter_type: rolling      # global | rolling
```

- **Per camera:** you set it on each camera.
- **Mixed rigs:** a rig can mix global- and rolling-shutter cameras freely.
- **Example:** the released 4-IMU/4-camera rig does exactly that.

In a camera–IMU config, you can estimate readout in the cam-IMU stage instead:

```yaml title="cam_imu.yaml"
camera_input:
  estimate_readout: true
```

## Why it is solved jointly

Readout is constrained by the same residuals as everything else. So it is not a
post-hoc correction with no derivative. A residual is the error between an
observed and a predicted image point.

This works because **one unified factor** (one error term in the solver) holds
all of these:

- projection
- time offset
- rolling shutter
- extrinsic composition
- SLERP pose interpolation (smooth blending between two poses)

We project a row's observation against the trajectory at *that row's* time,
not the frame's.

## What to expect

Readout is among the weakest parameters in the graph.

- **Needs fast motion:** only motion fast enough that rows see meaningfully
  different geometry excites it.
- **Slow recordings fail:** a slow, smooth recording will not constrain it.
- **Drift:** then the estimate drifts toward whatever the initialisation
  suggested.

Two checks are worth more than a single run's residual:

- **Repeatability.** Calibrate several sequences of the same rig with
  [batch mode](/guides/camera-imu-calibration/#batch-a-whole-dataset-family-from-one-config)
  and compare. A readout that moves between sequences was not observed in them.
- **Round-trip.** [`mvis roundtrip`](/guides/roundtrip/) catches a readout
  that absorbed error belonging to the time offset.

:::caution[Readout and time offset trade against each other]
Both shift *when* an observation is considered to have happened. With
insufficient motion the solver cannot separate them. The pair can then land
anywhere along a ridge (a line of equally good solutions) while the residual
stays flat. Is a rolling-shutter camera's `td` (its time offset) displaced
relative to its global-shutter neighbours? Suspect this before the hardware.
:::

## Reporting

- **HTML report:** readout appears in the temporal-calibration section, merged
  with the time offset. We read them together for the reason above.
- **Regression comparison reports:** they break out per-collection readout and
  time offset. This makes drift across a dataset family visible.

The residual and its Jacobians (its derivatives): [Camera model](/concepts/camera-model/).
