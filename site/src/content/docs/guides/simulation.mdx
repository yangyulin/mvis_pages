Use this page to tell *the estimator is wrong* apart from *the data was
insufficient*. The estimator is the solver that turns data into calibration
parameters.

In MVIS we build the synthetic data **from a real calibration**. So the
simulated rig is the rig you actually calibrated, not an idealised stand-in.

## The digital twin

A digital twin is a simulated copy of your rig with known true parameters.
`studies/calib_video_real.py` re-runs a calibration and renders it as a video.
With `--sim` it goes further:

1. It rebuilds a `GroundTruth` from the result.
2. It re-simulates every camera against that ground truth.
3. It renders a second video built from synthetic observations.

```bash
python studies/calib_video_real.py cam_imu.yaml --sim
```

The twin's true parameters are exactly the ones the real run reported. So any
disagreement between the two comes from the estimator, not the data.

## Closed-loop recovery

`--recover` calibrates the simulated data. It then prints the per-sensor error
of the recovered parameters against the ground truth they came from:

```bash
python studies/calib_video_real.py cam_imu.yaml --sim --recover
```

This is the sharpest check available. The synthetic data is generated by the
parameter's own value, with noise-free geometry and a known answer. If a
parameter cannot be recovered from that, it will never be recovered from a
real bag.

A failure here is a modelling or observability problem, never a data-quality
one. Observability means whether the data can pin down a parameter at all.

## What the video shows

The video is rendered in the IMU world frame. It shows:

- **Trajectory:** grows up to the current time, with start and end markers
- **Detection-vs-reprojection panels**, one per camera:
  - labelled with the ROS topic or EuRoC folder
  - per-corner residuals coloured green/orange/red
  - board coverage
  - per-frame RMS
- **IMU curves:** position and orientation, with a moving cursor
- **Rig layout panel:** every camera and IMU drawn as a coordinate frame at its
  calibrated extrinsics (its position and rotation on the rig). It is zoomed to
  the rig and moves with the trajectory (`--rig-view=elev,azim`)

Videos land in `results/videos/`.

The rig panel is the fastest way to catch a sign error or a swapped sensor. A
mirrored or inside-out rig is obvious at a glance. In a table of numbers it is
nearly invisible.

## Ground-truth datasets

For real data, per-dataset ground truth lives in `examples/regression/gt/`.
Where a dataset has one, the regression dashboard annotates every parameter
with its deviation, e.g. `Δ +0.27% GT=190.97`. The deviation is colour-coded by
accuracy band. See [Evaluation & metrics](/reference/evaluation/).

## Without ground truth

We have two substitutes, strongest first:

1. **[Round-trip](/guides/roundtrip/)**: `mvis roundtrip` applies the
   calibration to its own bag and recalibrates. PASS requires IMU intrinsics to
   collapse *and* geometry to hold.
2. **Repeatability**: run a
   [batch sweep](/guides/camera-imu-calibration/#batch-a-whole-dataset-family-from-one-config)
   across sequences of the same rig. Parameters that move between sequences
   were not constrained by the motion in them.

:::note[No synthetic-scenario generator yet]
MVIS simulates *from a calibration*. There is no authored-trajectory generator
for exploring motions you have not recorded. So degeneracy studies still need
real sequences with restricted motion. Degeneracy means a motion that leaves
some parameters undetermined.

The missing generator is tracked on the [roadmap](/about/roadmap/); the theory is in
[Degeneracy](/concepts/degeneracy/).
:::
