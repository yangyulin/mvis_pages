Use this page to solve each camera's lens and the camera-to-camera extrinsics.
You need a bag from [step 2](/guides/calibration-motion/). You get a camera YAML
that [step 4](/guides/camera-imu-calibration/) reads as its prior.

- **Intrinsics:** focal length and image centre of each camera.
- **Distortion:** how the lens bends straight lines.
- **Extrinsics:** where each camera sits relative to the others.
- **Our example:** the [VI-Rig 4 IMUs + 4 cameras](/datasets/virig-4imus-4cams/)
  dataset. It has a T265 fisheye pair (global shutter, 848 × 800) and an ELP
  pair (rolling shutter, 640 × 480).

## 1. Solve the cameras in pairs

The rig has two kinds of camera on two clocks. We solve each pair on its own.

- **T265 pair:** both fisheyes are global shutter and share one clock. Solve
  them together.
- **ELP pair:** both cameras are rolling shutter and share one clock. Solve
  them together.
- **Do not bundle the T265 with the ELP** in one camera-only solve. Their
  shutters differ and their clocks are far apart.
- **Between the pairs:** the extrinsics and time offsets (td) come from the
  joint camera–IMU solve in [step 4](/guides/camera-imu-calibration/).

The evidence is on [Why calibrate cameras together](/why/multi-camera/#4-when-not-to-bundle).

## 2. Write the T265 config

Save this as `t265_cam.yaml`, next to the bag:

```yaml title="t265_cam.yaml"
input:
  cameras:
  - camera_id: 2
    name: T265-1
    source_type: rosbag_topic
    source_path: 4imus_4cams_01.bag
    topic: /t265/fisheye1/image_raw
    distortion_model: kb4
    shutter_type: global
  - camera_id: 3
    name: T265-2
    source_type: rosbag_topic
    source_path: 4imus_4cams_01.bag
    topic: /t265/fisheye2/image_raw
    distortion_model: kb4
    shutter_type: global
board:
  board_type: apriltag
  rows: 6
  cols: 6
  tag_size: 0.088
  tag_spacing: 0.3
  tag_family: t36h11
solve:
  max_iterations: 15
  max_init_frames: 100
  pixel_sigma: 1.0
  huber_threshold: 1.345
output:
  path: t265_calib.yaml
  format: yaml
reference_camera: 2
estimate:
  board_points: true
corner_subsample: two_anti
```

- **`board:`:** the block from [step 1](/guides/board-setup/#2-the-board-in-the-running-example).
- **`corner_subsample: two_anti`:** two corners per tag, the default. See [Speed](#6-speed).
- **`estimate.board_points: true`:** solves the board shape too. See
  [A board is never flat](/guides/board-setup/#4-a-board-is-never-flat) · [why](/why/board-shape/).
- **`reference_camera: 2`:** the other camera's extrinsics are given relative to
  T265-1.
- **`shutter_type: global`:** no readout to solve.

Run it:

```bash title="shell"
mvis cam -c t265_cam.yaml
```

- **`-o` / `--output`:** the run folder for the report, logs and detection
  cache. By default it is an `ablation` folder next to `output.path`.

## 3. Choose a fisheye model for the T265

Set `distortion_model` per camera. MVIS has eight models:

- `radtan`, `equidistant`, `fov`, `double_sphere`, `eucm`, `ucm`,
  `omni_radtan`, `kb4`
- **Fisheye default:** `kb4`. The names `fisheye` and `kannala_brandt` also
  mean `kb4`.
- **Removed:** `kb8`. MVIS refuses it.
- **Normal lenses:** `radtan`.
- **Mixed rigs:** each camera can use its own model.

**kb4 and equidistant are the same on the T265.**

- **Why:** they share one polynomial. They differ only for rays more than 90°
  off axis.
- **T265 coverage:** on recording 01 the board corners stay under 80° off
  axis in the T265 images.
- **Checked:** in our T265 model study every reprojection number of the two models agreed
  to about 2e-6 px.
- **So:** the regression rows that use `equidistant` stand for `kb4` too.
- **Past 90°:** `equidistant` cannot project those rays; `kb4` can. See
  [Why kb4](/why/kb4/).

How the models compare on the T265 (our study on the 5-IMU rig,
[virig-5imus-4cams](/benchmark/results/virig-5imus-4cams/), 7 recordings, same
T265 model):

| Model | Verdict | What we saw |
|---|---|---|
| `kb4` / `equidistant` | **Use this** | Lowest error at the image edge, most repeatable between recordings |
| `eucm` | Usable | 9–12 % higher edge error (outer-bin p95); 1.57× the smallest spread |
| `double_sphere` | Avoid | 3.10× the smallest spread; needs bounds in cam-IMU |
| `omni_radtan` | Avoid | 2.93× the smallest spread; needs bounds in cam-IMU |
| `fov` | Avoid | 3.39× the smallest spread |
| `radtan` | Fails | Cannot follow the lens |

- **Spread:** how far each recording's fit moves the projected pixels,
  compared with the most central fit. The ratio is for the worst camera,
  against the model with the smallest spread on that camera.
- **Bounds:** with free intrinsics in cam-IMU, the double sphere focal length
  went negative on 4 of 7 recordings, omni-radtan on 3 of 7. Set
  `solve.bound_intrinsics: true` in the step 4 config if you use them.

To try another model, change only the `distortion_model` line on both cameras:

## 5. Write the ELP config

The ELP pair uses the same shape. Only the camera block and the reference
camera change:

```yaml title="elp_cam.yaml"
input:
  cameras:
  - camera_id: 0
    name: ELP-L
    source_type: rosbag_topic
    source_path: 4imus_4cams_01.bag
    topic: /elp/split_sync_image_node/left/image_raw
    distortion_model: equidistant
    shutter_type: rolling
  - camera_id: 1
    name: ELP-R
    source_type: rosbag_topic
    source_path: 4imus_4cams_01.bag
    topic: /elp/split_sync_image_node/right/image_raw
    distortion_model: equidistant
    shutter_type: rolling
# board:, solve: and estimate: as in t265_cam.yaml
output:
  path: elp_calib.yaml
  format: yaml
reference_camera: 0
```

```bash title="shell"
mvis cam -c elp_cam.yaml
```

- **`distortion_model: equidistant`:** what our ELP runs use.
- **`shutter_type: rolling`:** `mvis cam` then solves each ELP camera's readout.
  Readout details are in [step 5](/guides/rolling-shutter/).

## 6. Speed

`corner_subsample` picks how many corners per tag enter the solve. The camera-only
default is `two_anti`.

```yaml title="t265_cam.yaml"
corner_subsample: two_anti     # two_anti | two_diag | all | top_left
```

- **`two_anti` (default):** 2 corners per tag, top-left and bottom-right. About 20 % faster than `all`, and cx, cy stay put.
- **`two_diag`:** 2 corners per tag, the other diagonal.
- **`all`:** 4 corners per tag. Most data, no speed-up.
- **`top_left`:** 1 corner per tag, fastest. The fit is unchanged, but cx and
  cy can shift by up to about 0.8 px.
- **`factor_hz`:** the frame rate used per camera, 10 Hz by default. Set it
  lower to use fewer frames from a long recording.

## 7. Read the report

MVIS writes:

- **`output.path`:** the result to deploy. Step 4 reads this file.
- **`*_calib.yaml`:** the same result, in the run folder.
- **`*_full.yaml`:** the result plus board poses, to replay the run.
- **`.log`:** the run log, in the run folder.
- **HTML report:** self-contained.

Check the **motion-excitation grade** before the reprojection error. It is in the
report's Data Quality section, folded by default. The grade says how well your
motion constrained the calibration. The reprojection error is the pixel gap
between seen and predicted corners. See [Evaluation & metrics](/reference/evaluation/).

## What the pipeline does

The failure messages name these stages, so they are worth knowing:

| Stage | What happens |
|---|---|
| Detection | Adaptive multi-scale AprilTag — probes scale 1.0, then up to 3 extra scales picked from the observed tag size; far boards get an upscaled crop |
| Quality gating | Corner subsample, pooled-pose filter (≥20% tags across cameras), per-corner ≥5 views, per-camera ≥3 views, ≥6 tags/frame |
| 1 | Per-camera init — vanishing-point focal + RANSAC PnP board poses + sanity check |
| 2 | Per-camera GTSAM refinement, with rolling-shutter readout if enabled |
| 3 | Trajectory alignment — extrinsics via RANSAC; time offsets (only with `optimize_time_offset: true`) via PnP and homography cross-correlation |
| 4 | Joint multi-camera factor graph — the unified factor, all parameters |
| 5 | Outlier-driven rerun with pathology guardrail |
