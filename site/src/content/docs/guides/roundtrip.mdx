Use this page to check the calibration without ground truth. You need the
cam-IMU config from [step 4](/guides/camera-imu-calibration/). You get PASS
or FAIL.

- **Reprojection error** (how far detected corners land from where the
  calibration predicts them) tells you a calibration fits its own data. It
  does not tell you the calibration is right.
- **A round trip** does. We apply the calibration to the data it came from,
  then calibrate again. If the first answer was right, there is nothing left
  to find.

<RoundtripDiagram />

## 1. Run it

```bash
mvis roundtrip -c virig_4imus_4cams_cam_imu.yaml
```

One command runs four steps:

1. Calibrate.
2. Correct the bag with [`apply-calib`](#export-a-corrected-dataset).
3. Recalibrate the corrected bag.
4. Report PASS or FAIL.

It exits non-zero on FAIL, so it can run in CI.

| Flag | Effect |
|---|---|
| `-c`, `--config` | The cam-IMU config to check (ROS1 bag) |
| `--out` | Output folder for the report |
| `--bag` | Use this ROS1 bag instead of the config's source |
| `--keep-corrected` | Keep the corrected bag (deleted by default) |
| `--keep-bias` | Passed on to `apply-calib` |

The corrected bag gets its own name. So it gets a **fresh detection cache**
and does not reuse the original's.

## 2. What PASS means

PASS needs two things. They pull in opposite directions, which is what makes
the test useful.

- **Collapse.** On the corrected bag, every IMU's `Dw` and `Da` (the gyroscope
  and accelerometer scale and misalignment matrices) must go to identity.
  The biases `b_g` / `b_a` must go to zero. The first pass claimed to measure
  them. If it was right, the correction used them up.
- **Preserve.** Each camera's lever arm (its position in the base-IMU frame)
  must not move. Nor must the **stereo baseline**. Correction changes timing
  and IMU scaling, not geometry. A baseline that moves means the first solve
  traded geometry against something else.

The default limits:

- `Dw` and `Da`: within 1 % of identity.
- Biases: below 0.02 (rad/s for the gyroscope, m/s² for the accelerometer).
- Lever arms and stereo baseline: at most 2 mm of drift.

A residual `td` (the camera-to-IMU time offset) is a **warning, not a
failure**. How much of it survives depends on how well the data observes it.
A residual `t_ga` of the base IMU is also only a warning. Both warn above
2 ms.

## 3. Limits on this rig

- **Rolling shutter is not tested.** `apply-calib` re-stamps each frame but
  does not unwarp rolling-shutter rows. So a round trip on the ELP pair does
  not check its readout time.
- **Use other checks for the readout.** See
  [Rolling-shutter calibration](/guides/rolling-shutter/) and the
  [digital-twin check](/guides/simulation/).

## Export a corrected dataset

`mvis apply-calib` is the correction step inside the round trip. You can also
run it on its own. It takes a cam-IMU calibration and a raw ROS1 bag, and
writes a new bag with the calibration already applied:

- **IMU intrinsics** removed (scale, misalignment and g-sensitivity)
- **Bias** removed
- **One timeline** for every stream

Downstream tools then get corrected data. They need to know nothing about the
calibration.

### Run apply-calib

From a config, like the calibrator:

```bash
mvis apply-calib -c recalib.yaml
```

Or by flags:

```bash
mvis apply-calib --calib cam_imu_calib.yaml --in raw.bag --out corrected.bag
```

- **Calibration:** `cam-imu` writes `cam_imu_calib.yaml` next to
  `cam_imu.json`. Pass that YAML to `--calib`.
- **Output:** defaults to `<bag>.corrected.bag`.
- **Topics:** the calibration records each sensor's **source topic**. So the
  topic-to-sensor map is derived for you; there is none to write by hand.
- **Override:** use `--map` when you must override it.

Example config: `examples/configs/recalib_example.yaml` in the MVIS repo.

### What gets corrected

| Correction | Detail |
|---|---|
| IMU intrinsics | `Dw` / `Da` / `Tg` removed via the inverse model |
| Static bias | Removed, unless `--keep-bias` |
| Time alignment | Every camera and auxiliary IMU re-stamped onto the base-IMU timeline by its `td` |
| Gyro↔accel offset | Base-IMU accel channel re-interpolated at `t + t_ga`, when `t_ga` was calibrated |
| Undistortion | Images undistorted, with `--undistort` |

The terms in the table:

- **`Dw` / `Da`:** the scale and misalignment of the gyroscope and the
  accelerometer.
- **`Tg`:** the g-sensitivity, how linear acceleration leaks into the
  gyroscope.
- **`td`:** the time offset of a sensor against the base IMU.
- **`t_ga`:** the time offset between the gyroscope and the accelerometer.

A provenance sidecar is written next to the bag. It records what was applied.

:::caution[Re-stamping uses the header clock, not record time]
Correction is applied on each message's **header** clock. This is the most
important detail of the tool. Re-stamping on record time would bake each
topic's receive latency into the corrected bag. That turns a driver artefact
into permanent data.
:::

### Batch

A batch runner applies one calibration across a whole dataset family. This is
the usual case: one calibration per rig, many recordings.

- **TUM MIC05 and TUM-VI raw:** the correction is bit-exact. The corrected bag

- **T265** (July run, older code): the time offsets change as below.

## When it fails

A FAIL is a real finding, not a flaky test. The usual causes:

- **Wrong camera model.** The intrinsics absorbed error that comes back once
  timing is corrected. Try another
  [distortion model](/concepts/camera-model/).
- **Wrong IMU convention.** See [IMU model](/concepts/imu-model/).
- **An interpolated accelerometer** corrupting `td`. This is the T265 case.
  The fix is `gyro_only` on that IMU, or estimating `t_ga`. A self round trip
  does not catch this case by itself: a tool with no `t_ga` also returns to
  about zero on its own corrected bag. Turn `t_ga` on and read it, or run a
  correlation check. See [Why calibrate t_ga](/why/tga/).
- **Not enough motion.** The parameter was never observed, so correcting by
  it does nothing consistent.
