Evaluation & metrics

Use this page to tell whether a calibration is good. Check it in this order:

  1. Read the report: did the motion exercise every parameter?
  2. Run mvis verdict: are the fit and the values plausible?
  3. Run an independent check: round trip, repeatability, another tool or a digital twin.

The same metrics back the leaderboard, so a local run and a published entry measure the same thing.

1. Read the report first

Section titled “1. Read the report first”

Every run writes a self-contained HTML report (what is in it). Read its data quality section before the error numbers. It shows:

  • Motion excitation: grades for how much the motion moved each axis
  • Rotation-axis spread: whether you rotated about all three axes
  • Angular-velocity timeline: where in the recording the motion was
  • Image coverage: where the board corners fell in each image

Reprojection error is not accuracy

Reprojection error is the pixel distance between the detected and the predicted board corners. It says how well the result explains the data it was fitted to. A parameter the motion never excited stays near its start value without raising the error. A low error on a poorly excited recording means little.

2. Grade it with mvis verdict

Notes:

  • Pixel units: the reprojection thresholds are on the length of each corner’s 2D error, as Kalibr reports it. They are per-axis limits times √2: 1 and 2 px for the median and RMS, 2 and 4 px for the P95.
  • χ²/dof: the solve’s cost per degree of freedom. Near 1 means the noise settings match the data.
  • Warnings can be real: a raw consumer IMU can have a scale error above 5 %, and a USB camera a td above 50 ms. Confirm them across recordings.
  • ok: true from the solver only means it finished and passed its own gates. verdict never counts it as proof of a good fit.

3. Check it independently

Section titled “3. Check it independently”

mvis verdict --independent-check <kind> records which of these you ran.

Round trip

Section titled “Round trip”

It needs no ground truth. MVIS applies the calibration to its own bag and calibrates the corrected bag again. PASS needs every one of these on the corrected bag:

QuantityExpected after correctionTolerance
Dw, Da diagonals1within 0.01
Gyroscope and accelerometer bias0below 0.02 (rad/s, m/s²)
Lever and stereo baselineunchangedwithin 2 mm
td0above 2 ms is a warning only, because td can be weakly observable

The IMU terms must collapse to identity and zero while the geometry stays the same. See Round-trip validation.

Repeatability

Section titled “Repeatability”

Calibrate several recordings of one rig with input.bags and compare the results. A parameter that moves between recordings was not pinned down by the motion in them. See Camera–IMU calibration.

Another tool

Section titled “Another tool”

Run Kalibr or Basalt on the same recordings. mvis.io.kalibr reads Kalibr’s camchains and results (Kalibr files). The leaderboard shows MVIS, Kalibr and Basalt side by side.

Digital twin

Section titled “Digital twin”

A digital twin replays a real recording’s motion, frame times and corner layout with known parameters. Solving it measures bias against a truth no one gave the solver. See Digital-twin check.

Benchmark metrics

Section titled “Benchmark metrics”

The leaderboard and each dataset’s eval page use these numbers. Methodology explains how to read them.

Differenceper parameterDifference of two tools’ medians; ◆ when it is larger than the larger of the two spreads
Focal length, principal pointpxCamera intrinsics
Lever armmmCamera position in the base IMU frame, or auxiliary IMU position
Rotationradlog(R) rotation vector of an extrinsic
Stereo baselinemmDistance between two cameras
td, t_gamsCamera–IMU and gyro-to-accelerometer time offsets

The benchmark datasets have no ground truth. A small spread shows repeatability, not accuracy, and a difference shows that two tools disagree, not which one is right. Reprojection error is not compared across tools, because it measures fit.

Reference values

Section titled “Reference values”

Where a recording has published or factory values, the regression suite reports the percentage difference to them (--gt). These values are compared, never used as a pass or fail gate. They are kept with the regression suite.

Regression suite

Section titled “Regression suite”

We run MVIS over real recordings and digital twins, and gate every change against stored baselines with per-metric tolerances (focal length, distortion, extrinsics, time offsets, readout, reprojection). The runner and its baselines stay with the maintainers, not in the public repository; the commands below are how we run it. See Regression testing for the tests you can run.

--levelRuns
fastThe first recording of each family: the gate for every change
midThree recordings per family
fullEvery recording of every family
optionalRows outside the gates, such as camera-model variants
allfull and optional

--help prints the current row counts. --update-baseline rewrites the stored baselines after an intended change; the baseline diff then shows every number the change moved. How the suite is built: Regression testing.
