Result formats

Use this page to see what a run writes and which file to use for what.

RunFilesUse for
mvis cam<name>_calib.yaml, <name>_full.yaml, <name>.html, <name>.logDeploy the _calib.yaml; keep the rest to reproduce the run
mvis cam-imucam_imu.json, cam_imu_calib.yaml, cam_imu_camchain-imucam.yaml, cam_imu_report.htmlRead the JSON; deploy or apply the _calib.yaml; give Kalibr users the camchain
mvis apply-calib<bag>.corrected.bag, <bag>.corrected.bag.recalib.yamlThe corrected recording and how it was made
mvis roundtripforward/, recal/, report.txt, report.jsonPASS or FAIL with every check

Rotations are stored as matrices (3×3 or 4×4) or log(R) rotation vectors in radians, never roll, pitch and yaw. Board tilt against gravity is the one angle given in degrees.

Camera-only results

Section titled “Camera-only results”

mvis cam writes into the run folder (-o; by default a folder named ablation next to output_file). <name> is <config folder>_<config file name>: -c t265/cam.yaml gives t265_cam_calib.yaml.

FileContainsUse for
<name>_calib.yamlIntrinsics, distortion, extrinsics, time offsets, readout, reprojection statisticsDeploy. The calibration itself
<name>_full.yamlThe above, plus per-frame board poses, board corners, timings, filter statistics, motion metricsReplay. Rebuild the report or the 3D view without detecting again
<name>.htmlThe reportRead it first; see below
<name>.logThe run logDebugging
detections.mvisdbDetections and this run’s estimatesSee Capture database

With rerun_outliers: true, the first pass is kept as <name>_pass1_calib.yaml, <name>_pass1_full.yaml and <name>_pass1.html when it differs from the final result. The config’s output_file gets a copy of the result, in YAML or JSON (output_format).

Fields of _calib.yaml

Section titled “Fields of _calib.yaml”
FieldMeaning
cameras[]Per camera: id, model (pinhole_<distortion model>), intrinsics (fx, fy, cx, cy), distortion (model, coeffs), image_size, rolling_shutter_readout (s)
cameras[].rolling_shutter_readout_sigmaFormal 1σ of the readout (s), when it was estimated
cameras[].valid_domainkb4 only: the largest angle the fit can project, up to the model’s first fold
extrinsicsreference_camera and transforms[]: from, to, T_to_from (4×4), so3 (log(R), rad), translation (m)
time_offsetsreference_camera and offsets[]: camera, dt (s)
reprojection_errorsoverall_rms and per_camera[]: rms, mean, median, p90, p95, max (px), num_observations
board_shapeWith estimate.board_points: true: heights_m per corner, rms_mm, peak_to_peak_mm, n_obs
board_point_biasMean residual per board corner: median_px, max_px, n_points_seen
corner_accountingWhat became of every detected corner; see below

cam_imu_camchain-imucam.yamlKalibr camchain-imucamTools that read Kalibr files

cam_imu_sensor_clock.jsonPer-frame stamp maps, with retime_sensor_clockcamera_input.cameras[i].retime_map of a later run

td convention: an image stamped t matches the IMU at t + td.

Dw and Da compare only between calibrations with the same imu.model. Check the model before you compare numbers. See IMU model.

Corner accounting

Section titled “Corner accounting”

Every result has a corner_accounting block per camera. It says what happened to each detected corner, so a fit cannot look better by silently dropping corners. Every corner lands in exactly one category: detected = used + past_fold + other_invalid + outliers + no_pose_corners + not_in_solve.

FieldMeaning
detectedEvery corner given to the solve
usedHad a factor in the final solve and projects at the final fit
past_foldFails to project at the final fit, at or past a Kannala–Brandt model’s fold
other_invalidFails to project for another reason, for example behind the camera under equidistant
outliersRemoved by the outlier filter; still projects
no_pose_frames, no_pose_cornersFrames, and their corners, that reached no factor (no pose, too few points)
not_in_solveNever reached the final solve: thinned by rate or corner_subsample, or dropped by a gate
past_fold_pass1past_fold at the first pass’s fit, before the outlier rerun. Above zero also raises the alarm
n_cornersused + past_fold + other_invalid
max_theta_deg, max_theta_used_degLargest angle from the optical axis, of all corners and of the used ones
fold_deg, fold_levelkb4: angle of the fold. fold_level is alarm when corners lie past the fold, warn when the fold lies inside the image, else none

HTML reports

Section titled “HTML reports”

Every run writes one self-contained HTML file. It has no external files, so you can mail it. It prints cleanly and has a dark mode.

The camera-only report has:

  • Summary: stat cards and a table of contents
  • Intrinsics and distortion: tables per camera
  • Extrinsics: a table and a 3D plot
  • Temporal calibration: time offsets and readout
  • Reprojection: per-frame median and P95, per tag, error-vector histograms, corner heatmaps
  • Data quality: motion-excitation grades, rotation-axis spread, angular-velocity timeline, image coverage
  • Detection statistics, pipeline timing and collapsible appendices

The camera–IMU report adds:

  • Summary: status, reprojection RMS, χ²/dof, with grade badges
  • 3D views: the sensor rig (each camera at its T_CtoI, each auxiliary IMU, levers in mm) and the recovered trajectory with the board
  • Cameras, base IMU, auxiliary IMUs: every estimate, with its 1σ where the solve gives one
  • Against reference: lever, rotation and baseline differences, when the config has a reference: block

The reprojection and χ²/dof badges use the same thresholds as mvis verdict. See Evaluation & metrics.

Corrected bags

Section titled “Corrected bags”

mvis apply-calib writes an ordinary ROS1 bag. Anything that read the raw bag reads the corrected one. Next to it, <bag>.recalib.yaml records:

  • the source bag and the calibration file, with its SHA-256
  • the base IMU topic and the timeline (base_imu_clock, or the original stamps with --no-td)
  • the td convention: t_on_base = t_sensor + td
  • which corrections ran: remove_bias, undistort, imu_intrinsics, td, t_ga
  • which topics were corrected and which were copied unchanged

Kalibr files

Section titled “Kalibr files”

mvis.io.kalibr reads and writes Kalibr files:

FunctionDirectionDoes
read_camchaininA Kalibr camchain → per-camera intrinsics, distortion, resolution
read_camchain_imucaminAlso each camera’s T_cam_imu and the stereo T_cn_cnm1
write_camchain_imucamoutA camera–IMU result → a camchain-imucam dict
AprilTagBoard.from_kalibr_yamlinA Kalibr AprilGrid target file (in mvis.detection.apriltag_board)

So a Kalibr calibration can be an MVIS start (camera_input.path takes a camchain), and an MVIS result can go to tools that expect Kalibr. Notes on the exported camchain-imucam:

  • kb4: written as Kalibr pinhole + equidistant with the same coefficients. Exact for points in front of the camera; MVIS warns when the fit used corners past 90°.
  • Readout: written as Kalibr’s line_delay, the readout divided by the image rows.
  • rostopic: written as /camN/image_raw; set your own topics before you use the file with Kalibr.
  • Skipped export: when a camera cannot be expressed in Kalibr’s form (for example ucm with α outside [0, 1)), the camchain is not written and MVIS logs a warning. The MVIS files still hold the full result.
