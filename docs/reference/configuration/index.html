Configuration

Use this page to look up any key in an MVIS config file. One YAML file describes the board, the inputs and the solve. There are two config types:

  • Camera-only (mode: cam): calibrates the cameras alone.
  • Camera–IMU (mode: cam-imu): adds one or more IMUs (inertial measurement units: gyroscope and accelerometer) to a camera rig.

mvis run reads mode: to pick the pipeline; mvis cam and mvis cam-imu ignore it. For the commands, see the CLI reference.

Checked against MVIS 0.1.0

We wrote this page by hand from the MVIS 0.1.0 config code. Run mvis check -c config.yaml to lint a file: the solver only logs an unknown key and goes on, check reports it.

Rules for every config

Section titled “Rules for every config”
  • Paths: ${VAR} expands to the environment variable and a leading ~ to your home folder. ${MVIS_DATASETS} defaults to a Datasets folder in your home directory.
  • Units: lengths in metres, times in seconds, angles in radians, unless a key says otherwise.
  • Unknown keys: logged as a warning and ignored.
  • Aliases: target_hz is read as factor_hz; sigma_px and pixel_sigma are read as each other; pin_tr: true is read as estimate_readout: false.
  • Camera models: radtan, equidistant, kb4, fov, double_sphere, eucm, ucm, omni_radtan (experimental). fisheye and kannala_brandt mean kb4 (why). See Camera model.

estimate

Section titled “estimate”

The estimate: block says what is solved and what is held fixed. Both config types read it. It wins over the older low-level keys it maps to (the parser warns when both are set). Leave a key out to keep the default.

camera.intrinsicstrueSolve the intrinsicsRefine the prior intrinsics; false pins them to camera_input.path
camera.distortiontrueNot read: the solver always estimates distortionFollows camera.intrinsics
camera.trfalseNot read: set shutter_type: rolling on the cameraSolve the readout of rolling-shutter cameras
camera.tdcamera-only false, camera–IMU trueCamera–camera time offsets (unsynchronised cameras)Camera to base-IMU time offset
camera.extrinsicstrueNot read: always estimatedSolve T_CtoI
imu.intrinsicsdw_da—pinned, dw_da (scale and misalignment), dw_da_r (plus the gyro-to-accelerometer rotation), full (plus Tg); true = full, false = pinned
imu.modelcalyx—kalibr, rpng or calyx: a convention, see IMU model
imu.extrinsicstrue—Solve each auxiliary IMU’s pose in the base IMU frame

A false on a camera–IMU key adds a very tight prior that holds the value at its start. Board heights carry a weak 3 mm prior (solve.board_height_sigma on camera–IMU). Their mean and the two tilts are held at zero, so the board pose keeps the plane.

VI-Rig: estimate the board shape

The VI-Rig AprilGrid is not flat. Set estimate.board_points: true in every VI-Rig config, camera-only and camera–IMU. Other boards keep the default unless you measured them non-flat. See Board shape.

optimizer / solve

Section titled “optimizer / solve”
KeyDefaultMeaning
max_iterations200Levenberg–Marquardt (LM) iterations of the joint solve
max_init_frames100Frames used for the first guess; 0 = no cap
init_frame_selectionuniformuniform (spaced in time) or diverse (spread over position, size and tilt)

lm_lambda_lower, lm_lambda_upper0, 100LM damping bounds

Four nested groups hold expert settings. Their defaults suit most rigs:

  • frame_quality: detection gates, for example min_tags_per_frame: 6, min_corner_views: 5, max_pnp_reprojection_px: 10.
  • trajectory_alignment: first guess of extrinsics and time offsets, for example max_expected_dt_s: 0.5.
  • outlier_rejection: the second pass, for example enabled: true, threshold_px: 2.0, percentile: 99.
  • guardrail: when to fall back to the first pass, for example p95_regression_factor: 1.5.

Top-level keys

Section titled “Top-level keys”
KeyDefaultMeaning
modecamcam or cam-imu; read by mvis run
reference_camera0Camera the extrinsics are expressed in
corner_subsampletwo_antiCorners kept per AprilGrid tag. See below
optimize_time_offsetfalseSolve camera–camera time offsets; for unsynchronised cameras
rerun_outlierstrueRun a second pass without outliers; it falls back to the first pass if the second one goes wrong
rerun_visualizationfalseOpen the Rerun 3D viewer (needs the viz extra)
output_filecalibration_result.yamlResult path (flat shape)
output_formatyamlyaml or json (flat shape)
report.thumbnail_max_dim320Size of detection thumbnails in the report (px)

corner_subsample values:

  • two_anti (camera-only default): two diagonal corners per tag. Faster than all, and in our runs on VI-Rig and TUM-VI (MVIS 0.1.0) the principal point stayed within about 0.1 px of it.
  • two_diag: the other diagonal pair.
  • all (camera–IMU default): every corner.
  • top_left, top_right, bottom_left, bottom_right (or tl, tr, bl, br): one corner per tag. Fastest, but in the same runs it moved cx and cy by up to about 0.8 px, and reprojection error does not show it.

With few tags it falls back to all. The first guess always uses every corner. The sectioned shape also accepts solve.corner_subsample; the top-level key wins.

Camera–IMU config

Section titled “Camera–IMU config”

Top-level sections: input, board, camera_input, solve, estimate, output and the optional reference. Camera–IMU calibration is two steps:

  1. Calibrate the cameras (camera-only config).
  2. Give that result to camera_input.path and solve with the IMUs.

Section titled “camera_input”
KeyDefaultMeaning

camera_input.cameras[i] accepts free_intrinsics, estimate_readout, rolling_mode, factor_hz (vision factors per second for that camera) and vision_pose (imu or interp). For cameras whose stamps are not on the sensor clock, retime_sensor_clock: true solves a per-frame capture offset first, and retime_map reuses the <output>_sensor_clock.json of an earlier run.

solve

Section titled “solve”

Three terms first:

  • td: the camera–IMU time offset.
  • t_ga: the time offset between the gyroscope and accelerometer of one IMU (why).
  • State: the IMU pose, velocity and biases at one instant; states are placed at state_hz.
