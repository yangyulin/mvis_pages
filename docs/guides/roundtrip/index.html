Round-trip validation

Use this page to check the calibration without ground truth. You need the cam-IMU config from step 4. You get PASS or FAIL.

  • Reprojection error (how far detected corners land from where the calibration predicts them) tells you a calibration fits its own data. It does not tell you the calibration is right.
  • A round trip does. We apply the calibration to the data it came from, then calibrate again. If the first answer was right, there is nothing left to find.

1. Run it

Section titled “1. Run it”

One command runs four steps:

  1. Calibrate.
  2. Correct the bag with apply-calib.
  3. Recalibrate the corrected bag.
  4. Report PASS or FAIL.

It exits non-zero on FAIL, so it can run in CI.

FlagEffect
-c, --configThe cam-IMU config to check (ROS1 bag)
--outOutput folder for the report
--bagUse this ROS1 bag instead of the config’s source
--keep-correctedKeep the corrected bag (deleted by default)
--keep-biasPassed on to apply-calib

The corrected bag gets its own name. So it gets a fresh detection cache and does not reuse the original’s.

2. What PASS means

Section titled “2. What PASS means”

PASS needs two things. They pull in opposite directions, which is what makes the test useful.

  • Collapse. On the corrected bag, every IMU’s Dw and Da (the gyroscope and accelerometer scale and misalignment matrices) must go to identity. The biases b_g / b_a must go to zero. The first pass claimed to measure them. If it was right, the correction used them up.
  • Preserve. Each camera’s lever arm (its position in the base-IMU frame) must not move. Nor must the stereo baseline. Correction changes timing and IMU scaling, not geometry. A baseline that moves means the first solve traded geometry against something else.

The default limits:

  • Dw and Da: within 1 % of identity.
  • Biases: below 0.02 (rad/s for the gyroscope, m/s² for the accelerometer).
  • Lever arms and stereo baseline: at most 2 mm of drift.

A residual td (the camera-to-IMU time offset) is a warning, not a failure. How much of it survives depends on how well the data observes it. A residual t_ga of the base IMU is also only a warning. Both warn above 2 ms.

3. Limits on this rig

Section titled “3. Limits on this rig”
  • Rolling shutter is not tested. apply-calib re-stamps each frame but does not unwarp rolling-shutter rows. So a round trip on the ELP pair does not check its readout time.
  • Use other checks for the readout. See Rolling-shutter calibration and the digital-twin check.

Export a corrected dataset

Section titled “Export a corrected dataset”

mvis apply-calib is the correction step inside the round trip. You can also run it on its own. It takes a cam-IMU calibration and a raw ROS1 bag, and writes a new bag with the calibration already applied:

  • IMU intrinsics removed (scale, misalignment and g-sensitivity)
  • Bias removed
  • One timeline for every stream

Downstream tools then get corrected data. They need to know nothing about the calibration.

Run apply-calib

Section titled “Run apply-calib”

From a config, like the calibrator:

Or by flags:

  • Calibration: cam-imu writes cam_imu_calib.yaml next to cam_imu.json. Pass that YAML to --calib.
  • Output: defaults to <bag>.corrected.bag.
  • Topics: the calibration records each sensor’s source topic. So the topic-to-sensor map is derived for you; there is none to write by hand.
  • Override: use --map when you must override it.

Example config: examples/configs/recalib_example.yaml in the MVIS repo.

What gets corrected

Section titled “What gets corrected”
CorrectionDetail
IMU intrinsicsDw / Da / Tg removed via the inverse model
Static biasRemoved, unless --keep-bias
Time alignmentEvery camera and auxiliary IMU re-stamped onto the base-IMU timeline by its td
Gyro↔accel offsetBase-IMU accel channel re-interpolated at t + t_ga, when t_ga was calibrated
UndistortionImages undistorted, with --undistort

The terms in the table:

  • Dw / Da: the scale and misalignment of the gyroscope and the accelerometer.
  • Tg: the g-sensitivity, how linear acceleration leaks into the gyroscope.
  • td: the time offset of a sensor against the base IMU.
  • t_ga: the time offset between the gyroscope and the accelerometer.

A provenance sidecar is written next to the bag. It records what was applied.

Re-stamping uses the header clock, not record time

Correction is applied on each message’s header clock. This is the most important detail of the tool. Re-stamping on record time would bake each topic’s receive latency into the corrected bag. That turns a driver artefact into permanent data.

Batch

Section titled “Batch”

A batch runner applies one calibration across a whole dataset family. This is the usual case: one calibration per rig, many recordings.

When it fails

Section titled “When it fails”

A FAIL is a real finding, not a flaky test. The usual causes:

  • Wrong camera model. The intrinsics absorbed error that comes back once timing is corrected. Try another distortion model.
  • Wrong IMU convention. See IMU model.
  • An interpolated accelerometer corrupting td. This is the T265 case. The fix is gyro_only on that IMU, or estimating t_ga. A self round trip does not catch this case by itself: a tool with no t_ga also returns to about zero on its own corrected bag. Turn t_ga on and read it, or run a correlation check. See Why calibrate t_ga.
  • Not enough motion. The parameter was never observed, so correcting by it does nothing consistent.
