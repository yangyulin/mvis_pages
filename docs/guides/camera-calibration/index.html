Camera-only calibration

Use this page to solve each camera’s lens and the camera-to-camera extrinsics. You need a bag from step 2. You get a camera YAML that step 4 reads as its prior.

  • Intrinsics: focal length and image centre of each camera.
  • Distortion: how the lens bends straight lines.
  • Extrinsics: where each camera sits relative to the others.
  • Our example: the VI-Rig 4 IMUs + 4 cameras dataset. It has a T265 fisheye pair (global shutter, 848 × 800) and an ELP pair (rolling shutter, 640 × 480).

1. Solve the cameras in pairs

Section titled “1. Solve the cameras in pairs”

The rig has two kinds of camera on two clocks. We solve each pair on its own.

  • T265 pair: both fisheyes are global shutter and share one clock. Solve them together.
  • ELP pair: both cameras are rolling shutter and share one clock. Solve them together.
  • Do not bundle the T265 with the ELP in one camera-only solve. Their shutters differ and their clocks are far apart.
  • Between the pairs: the extrinsics and time offsets (td) come from the joint camera–IMU solve in step 4.

The evidence is on Why calibrate cameras together.

2. Write the T265 config

Section titled “2. Write the T265 config”

Save this as t265_cam.yaml, next to the bag:

  • board:: the block from step 1.
  • corner_subsample: two_anti: two corners per tag, the default. See Speed.
  • estimate.board_points: true: solves the board shape too. See A board is never flat.
  • reference_camera: 2: the other camera’s extrinsics are given relative to T265-1.
  • shutter_type: global: no readout to solve.

Run it:

  • -o / --output: the run folder for the report, logs and detection cache. By default it is an ablation folder next to output.path.

3. Choose a fisheye model for the T265

Section titled “3. Choose a fisheye model for the T265”

Set distortion_model per camera. MVIS has eight models:

  • radtan, equidistant, fov, double_sphere, eucm, ucm, omni_radtan, kb4
  • Fisheye default: kb4. The names fisheye and kannala_brandt also mean kb4.
  • Removed: kb8. MVIS refuses it.
  • Normal lenses: radtan.
  • Mixed rigs: each camera can use its own model.

kb4 and equidistant are the same on the T265.

  • Why: they share one polynomial. They differ only for rays more than 90° off axis.
  • T265 coverage: on recording 01 the board corners stay under 80° off axis in the T265 images.
  • Checked: in our T265 model study every reprojection number of the two models agreed to about 1e-6 px.
  • So: the regression rows that use equidistant stand for kb4 too.

How the models compare on the T265 (our study on the 5-IMU rig, virig-5imus-4cams, 7 recordings, same T265 model):

ModelVerdictWhat we saw
kb4 / equidistantUse thisLowest error at the image edge, most repeatable between recordings
eucmUsable9–12 % higher edge error (outer-bin p95); 1.57× the smallest spread
double_sphereAvoid3.10× the smallest spread; needs bounds in cam-IMU
omni_radtanAvoid2.93× the smallest spread; needs bounds in cam-IMU
fovAvoid3.39× the smallest spread
radtanFailsCannot follow the lens
  • Spread: how far each recording’s fit moves the projected pixels, compared with the most central fit. The ratio is for the worst camera, against the model with the smallest spread on that camera.
  • Bounds: with free intrinsics in cam-IMU, the double sphere focal length went negative on 4 of 7 recordings, omni-radtan on 3 of 7. Set solve.bound_intrinsics: true in the step 4 config if you use them.

To try another model, change only the distortion_model line on both cameras:

  • kb4 (default)
  • double_sphere
  • eucm

The trade-offs in math are on Camera model.

5. Write the ELP config

Section titled “5. Write the ELP config”

The ELP pair uses the same shape. Only the camera block and the reference camera change:

  • distortion_model: equidistant: what our ELP runs use.
  • shutter_type: rolling: mvis cam then solves each ELP camera’s readout. Readout details are in step 5.

6. Speed

Section titled “6. Speed”

corner_subsample picks how many corners per tag enter the solve. The camera-only default is two_anti.

  • two_anti (default): 2 corners per tag, top-left and bottom-right. About 20 % faster than all, and cx, cy stay put.
  • two_diag: 2 corners per tag, the other diagonal.
  • all: 4 corners per tag. Most data, no speed-up.
  • top_left: 1 corner per tag, fastest. The fit is unchanged, but cx and cy can shift by up to about 0.8 px.
  • factor_hz: the frame rate used per camera, 10 Hz by default. Set it lower to use fewer frames from a long recording.

7. Read the report

Section titled “7. Read the report”

MVIS writes:

  • output.path: the result to deploy. Step 4 reads this file.
  • *_calib.yaml: the same result, in the run folder.
  • *_full.yaml: the result plus board poses, to replay the run.
  • .log: the run log, in the run folder.
  • HTML report: self-contained.

Check the motion-excitation grade before the reprojection error. It is in the report’s Data Quality section, folded by default. The grade says how well your motion constrained the calibration. The reprojection error is the pixel gap between seen and predicted corners. See Evaluation & metrics.

What the pipeline does

Section titled “What the pipeline does”

The failure messages name these stages, so they are worth knowing:

StageWhat happens
DetectionAdaptive multi-scale AprilTag — probes scale 1.0, then up to 3 extra scales picked from the observed tag size; far boards get an upscaled crop
Quality gatingCorner subsample, pooled-pose filter (≥20% tags across cameras), per-corner ≥5 views, per-camera ≥3 views, ≥6 tags/frame
1Per-camera init — vanishing-point focal + RANSAC PnP board poses + sanity check
2Per-camera GTSAM refinement, with rolling-shutter readout if enabled
3Trajectory alignment — extrinsics via RANSAC; time offsets (only with optimize_time_offset: true) via PnP and homography cross-correlation
4Joint multi-camera factor graph — the unified factor, all parameters
5Outlier-driven rerun with pathology guardrail

Section titled “Next”
  • Step 4: point camera_input.path at the camera YAML from this page. It takes one file, so join the T265 and ELP results into one YAML first. See Camera–IMU calibration. The cam-IMU solve refines the intrinsics further.
  • Renumber when you join: MVIS sorts the joined file’s cameras by id and matches them to cam_topics by order. Step 4 lists the T265 first, so give the T265 cameras id 0 and 1 and the ELP cameras 2 and 3. The configs on this page use other ids (ELP 0 and 1, T265 2 and 3).
  • Our example’s prior: the camera_prior.yaml of the example run joins two earlier camera-only results. The ELP pair is the median of the 15 ELP camera-only solves. The T265 pair comes from an older camera-only solve of the T265, not from the config on this page.
