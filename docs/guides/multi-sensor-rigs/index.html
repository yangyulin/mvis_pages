Multi-IMU spatial-temporal calibration

Step 6 of the walkthrough. Here you add more IMUs to the camera–IMU solve.

  • You need: the config from step 4.
  • You get: for every extra IMU, its lever arm and rotation to the base IMU, its time offset td and its t_ga.
  • Check: compare the numbers across recordings (section 3), and name the base IMU when you quote them.

Two terms:

  • Base IMU: the IMU every other sensor is measured against. It sets the clock and carries the trajectory.
  • Aux IMU (auxiliary IMU): any other IMU on the rig. MVIS solves where it sits and how its clock runs against the base.

All IMUs enter one factor graph with the cameras. There is no pairwise step.

The running example is VI-Rig: 4 IMUs + 4 cameras, bag 4imus_4cams_01.

1. Pick the base

Section titled “1. Pick the base”

The first entry in input.imu_topics is the base IMU. It is the reference clock for the whole rig and the only IMU that carries the trajectory. Every other entry is an aux IMU, in the order you list it.

In the running example the base is the Xsens (/imu/data):

  • Pick a good IMU as the base: its errors spread to the whole rig.
  • Say which base you used when you quote a number. A td or a lever means “against this base”.

Two bases on this dataset

The bag-01 run on this page uses the Xsens as base. The 15-bag runs on the results page that include IMUs use the T265 IMU as base, with the Xsens as the only aux IMU.

2. Turn on the aux spatial and temporal terms

Section titled “2. Turn on the aux spatial and temporal terms”

These keys in the step-4 config control the aux IMUs:

  • estimate.imu.extrinsics: solves each aux IMU’s lever and rotation. Default true.
  • estimate.imu.td: solves each aux IMU’s time offset to the base. Default true.
  • false on either holds that value at its start value instead.
  • solve.estimate_t_ga: t_ga is the delay between an IMU’s accelerometer and its gyroscope. One flag covers the base and the aux IMUs. Default true.
  • IMU intrinsics (scale and misalignment) follow estimate.imu.intrinsics for every IMU, base and aux. Step 4 sets it to dw_da.

An aux IMU with a bad accelerometer

Section titled “An aux IMU with a bad accelerometer”

Set gyro_only: true on that IMU. The entries in input.imus match input.imu_topics by order:

  • What it solves: rotation, td, Dw (gyroscope scale and misalignment) and gyroscope bias.
  • What it holds fixed: the lever and the accelerometer terms. There is no t_ga.
  • Not on the base: the base always needs its accelerometer. MVIS stops with an error if you set it there.

The running example does not need it: all four IMUs run in full mode. When to prefer it over t_ga: IMU model.

4. Sensor numbering when comparing with Kalibr

Section titled “4. Sensor numbering when comparing with Kalibr”

Both tools number sensors in input order, but they name the IMUs differently. Getting this wrong silently compares the wrong pair.

  • MVIS: cameras are cam0, cam1, … in input.cam_topics order. The base IMU, the first input.imu_topics entry, is imu0. Each aux IMU is named after the first part of its topic: /gx3_25/data becomes gx3_25, /t265/imu becomes t265, /imu/data becomes imu. These names appear in cam_imu.json, the calibration YAML and the HTML report.
  • Kalibr: cameras are cam0, cam1, …; imu0 is its reference IMU, the first IMU it is given, and the others are imu1, imu2, … in input order.
  • Same input order, same base: in the runs below both tools get the same topic lists, so imu0 is the same IMU in both. Match the aux IMUs by topic, not by number.

5. Several cameras

Section titled “5. Several cameras”

Cameras join the same graph. You set them up in step 3:

  • reference_camera: the camera the other cameras’ extrinsics are expressed against.
  • estimate.camera.td: true (camera-only): solves a time offset between cameras that are not synchronised.
  • Per-camera td: in the camera–IMU solve every camera gets its own td to the base IMU. In bag 01 the T265 cameras sit at −5.41 and −7.47 ms, the ELP cameras at −123.25 and −123.30 ms.
